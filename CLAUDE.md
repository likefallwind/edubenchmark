# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **research and benchmark-specification workspace** for AI-education evaluation, not a model-training or app codebase. The work is information collection, building a unified evaluation taxonomy, and indexing benchmark questions back to their original sources. The default language for reports and content is Chinese; scripts and code are English.

`AGENTS.md` holds the canonical contributor conventions (commit style, coding style, PR expectations). Read it for anything not covered here.

## The two benchmark generations

There are two parallel benchmark efforts. Know which one a task targets:

1. **Benchmark v1** (`*_2026_05_18`): the original spec built around **8 top-level scales (S1–S8)**, **24 atomic capabilities (D01–D24)**, 84 evaluation criteria, and 840 sampled items. Entry point `AI_EDU_BENCHMARK_V1.md`.
2. **RE_BENCHMARK_V1** (`re_benchmark_v1`): the newer **five-category** main-test reorganization (C1–C5), plus a runnable pilot package and a MiniMax smoke-test runner. Entry point `re_benchmark_v1.md`.

Both reuse the same D01–D24 capability taxonomy defined in `data/benchmark_metric_dimensions_2026-05-12.json` and the indicators in `data/benchmark_metric_indicators_2026-05-12.json`.

## Architecture: generate → emit triple → report

Every `scripts/build_*.py` follows the same pipeline and is **idempotent** — it reads taxonomy/source JSON, constructs candidate items, scores them, and overwrites its outputs. Never hand-edit generated files; change the build script and rerun.

- `build_benchmark_v1_2026_05_18.py`: taxonomy → candidate items (up to 80 per criterion) → transparent heuristic `quality_score` → keep top 10 → emit `items.jsonl` / `capability_criteria.jsonl` / `source_manifest.jsonl` plus the root `AI_EDU_BENCHMARK_V1.{md,html}` and `ai_edu_benchmark_v1_questions.json` and the `reports/2026-05-18/` spec.
- `build_exhaustive_2026_05_13.py`: emits the survey evidence base under `data/exhaustive_2026-05-13/` (benchmarks, metrics, results, dimension_mapping, dataset_acquisition) and `reports/2026-05-13/`.
- `build_re_benchmark_v1.py`: emits `data/re_benchmark_v1/` registry, source manifest, and pilot items.

Each item carries `source_file` + `source_row_or_key` for traceability back to a local dataset row. **`coverage_status: coverage_gap`** means an item is only a proxy / resource-construction sample — local material exists but the native benchmark label, licensed data, or multimodal/log resource does not. Do not treat coverage_gap items as full native coverage.

### Source status vocabulary

Manifests classify each source by access state, and this distinction is load-bearing throughout the repo: `local_ready`, `downloadable_not_local`, `manual_kaggle_required` / `manual_access_or_metadata_only`, `metadata_model_available_dataset_not_found`, `local_ready_but_no_pilot_extractor`. Gated/unpublished data (Kaggle ASAP, EssayJudge, HF-gated TutorBench/Pedagogy Benchmark) is recorded as an evidence gap — never assume it is reproducible.

### The runner (RE_BENCHMARK_V1)

`scripts/run_re_benchmark_v1.py` exports prompts, runs the MiniMax smoke test, and scores predictions. It separates three outcomes: **exact-match auto-scoring** for text items, **judge-needed** accounting for rubric/multimodal/code/safety items, and **format compliance** tracked separately from answer correctness. Predictions JSONL: `{"item_id": ..., "response": ..., "model": ...}`. For MCQ, options are reconstructed from source data and the model is asked for an option letter.

## The per-benchmark eval framework (`scripts/eval/`)

A separate, extensible harness for evaluating **one benchmark at a time** against an API model. It is deliberately decoupled from the dated build scripts and from `run_re_benchmark_v1.py` (which is text-only and refuses image items). Pipeline: **load items → call model (text [+ images]) → LLM answer extraction → score → report** under stable per-benchmark directories: `reports/eval/<benchmark>/<model-slug>/`.

- Entry point `scripts/eval_benchmark.py --benchmark <name>`. Phases are resumable/incremental: `predictions.jsonl` and `extractions.jsonl` are keyed by `item_id` and skipped on rerun; `--skip-extract` stops after predictions, `--score-only` reuses predictions, `--dry-run` prints constructed messages (base64 images elided) without calling the API.
- **Multi-provider** (`scripts/eval/providers.py`): one `MiniMaxClient` drives several OpenAI-compatible backends; `--model` is mapped to a provider by name prefix (longest match wins), unknown models fall back to the **gateway**. Three providers ship: `minimax` (`MINIMAX_API_KEY`, also home of the default extractor `MiniMax-M2.7`), `gateway` (a local relay at `http://127.0.0.1:8111/v1`, key env `API_GATEWAY`, serving `doubao-*`/`glm-*`/`deepseek-*` at `/chat/completions`), and `deepseek` (`https://api.deepseek.com`, key env `DEEPSEEK_API`, `deepseek-v4-pro`/`deepseek-v4-flash`). **`deepseek-*` models default to the gateway** (it serves them too); reach DeepSeek's official API only when specifically asked, via `--provider deepseek`. A fifth provider `zgc` (`https://zgc.apihy.com/v1`, key env `ZGC_API`) is registered for **exactly one model, `deepseek-v3.2`**, and is that model's **default route**: the gateway still lists `deepseek-v3.2` in `/models` but 404s `UnsupportedModel` on every call (verified 2026-07-18), and DeepSeek's official API has retired the V3.2 generation. **As of 2026-08-11 the ZGC `deepseek-v3.2` route is corrupting its own output and must not be used for judging or extraction**: it returns HTTP 200 with random tokens spliced into the reply (`"instruction_following": 打卡` / `Photon` / `корегт`; asked to echo `{"a": 3, "b": 7, "c": 5}` it returns `{"a": 3, "b":与合作方取得联系"}`), and short replies are unaffected so a one-line probe reads as healthy — verify with a **long-output echo probe** before trusting it again. The same fault period also produced runs of bare HTTP 400 `请求参数有误`. The edubench judge default moved off it to `MiniMax-M3` because of this. Other `deepseek-*` models are unaffected and still resolve to the gateway. Prefix resolution is genuinely **longest-match** (it used to be first-match despite the docstring), so the specific `deepseek-v3.2` entry beats the general `deepseek` one. Results under `reports/eval/<benchmark>/deepseek-v3.2/` that predate 2026-07-18 came from the gateway backend and are **not comparable** to ZGC-served runs — re-run rather than append. zgc also serves the reasoning variant **`deepseek-v3.2-think`**, which is registered and routes there by the same prefix; it returns its chain of thought in `reasoning_content` with only the answer in `content` (977 of 982 completion tokens were reasoning in a smoke test), so it is listed in `_REASONING_MODEL_PREFIXES` and must never be capped — the plain `deepseek-v3.2` reasons inline in `content` instead and is not listed. A sixth provider `silicon` (SiliconFlow, `https://api.siliconflow.cn/v1`, key env `SILICON_API`) serves vendor-prefixed open-weight models and is the **default route for the `Qwen/` prefix**; it is registered for `Qwen/Qwen3-8B`, which runs with thinking on by default — chain of thought in `reasoning_content`, answer only in `content` (7,300 of 7,309 completion tokens billed as reasoning on a one-line arithmetic prompt, 2026-07-28) — so it is in `_REASONING_MODEL_PREFIXES` and must never be capped; expect minutes of wall clock per item even on trivial prompts. To add another SiliconFlow model, extend the provider's `models` set and, if it thinks, `_REASONING_MODEL_PREFIXES`. A seventh provider `vllm` is a **self-hosted vLLM server on an A100-80GB box, the sole route for `Qwen/Qwen3.5-4B`** (moved off SiliconFlow by decision on 2026-08-10 — that model is served only from our own deployment now, so `silicon` no longer lists it and the longer `qwen/qwen3.5-4b` prefix wins over `qwen/`). It is the first **unauthenticated** provider: the server runs without `--api-key`, so `Provider.api_key_required=False` lets `build_client` send a placeholder bearer token instead of raising on an unset `VLLM_API_KEY`. Its output is **not comparable with the SiliconFlow runs of the same model**. The server's first configuration was unusable and was fixed on 2026-08-10 — it ran `--max-model-len 4096` (against a model whose native context is 262,144) with no `--reasoning-parser`, which truncated **27% of a 30-item mmlu_pro sample** mid-think, every one stopping at exactly 4,096 total tokens, and left the raw `<think>` block in `content`. It now runs `--max-model-len 65536` + `--reasoning-parser qwen3`; re-verified as 0 truncations with the trace split out (into the bare `reasoning` field, which `minimax_client` reads alongside `reasoning_content`). **Discard any run made before that fix.** Thinking is on by default and needs no request param; the trace arrives in the bare `reasoning` field, which `minimax_client` reads alongside `reasoning_content`. A third defect fixed the same day: `<|im_end|>` used to leak into `content` on every reply because the model snapshot was an incomplete download **missing `tokenizer_config.json`, `chat_template.jinja`, `vocab.json` and `merges.txt`** — with no `eos_token` declaration vLLM fell back to `config.json`'s `eos_token_id: 248044` (`<|endoftext|>`) while the real chat-turn terminator is `<|im_end|>`, and the absent template is why one had to be hand-written. (Qwen3.5-4B genuinely ships **no** `generation_config.json` upstream, and the odd `model.safetensors-0000N-of-00002` filenames are upstream too — neither is a symptom.) Fixed by fetching the four files at the pinned revision and dropping `--chat-template` so the official template loads. **Reaching it**: the public `http://115.190.90.101:63550/v1` works directly, but only because the server now listens on container port **3631** — the platform (a k8s pod behind NAT) maps public 63550 to 3631, the mapping cannot be changed from inside the container, and vLLM was originally started on 8000, which is why the public port answered with a RST. Starting it on any other port silently loses public access. The host's public 8000 is a *different* container running an sglang video model — do not mistake it for this service. `scripts/vllm_tunnel.sh` (SSH local forward) plus `VLLM_BASE_URL` remains as a fallback. **Run it at `--concurrency 64`** (decided 2026-08-10): output throughput scales 959 → 1796 → 3025 → 4618 → 5512 → 5587 tok/s at 8/16/32/64/96/128 concurrent, so marginal gain falls to 1.17× for 48→64, 1.19× for 64→96 and **1.01× for 96→128**. The plateau is GPU compute saturation rather than the `--max-num-seqs 128` ceiling — per-stream speed falls 120 → 57 tok/s exactly mirroring it, `Waiting` stayed 0, and TTFT rose smoothly (0.16 → 1.23s p95) instead of stepping the way queueing would. Drop to 32 if someone is using the service interactively at the same time. Re-measure with `scripts/bench_vllm_concurrency.py`, which **must** keep its fixed-output-length design (`max_tokens` + `ignore_eos`): the first attempt used variable-length greedy output and spent the last 7 of its 27 minutes draining a *single* request, deflating 16-way throughput to 882 tok/s against the 1,796 tok/s the controlled run measures. A provider may declare a `models` allowlist, which `build_client` enforces up front. Entries in `_MODEL_PARAMS` carry an optional **provider scope**, since such params are usually per-relay workarounds and must not leak across providers and violate the no-`max_tokens` policy. Default prediction model is `MiniMax-M3`. (Gateway usage details + the `API_GATEWAY` non-interactive-shell gotcha live in memory `eval-gateway-multimodel`.)
- `scripts/eval/minimax_client.py`: MiniMax's OpenAI-compatible endpoint `<MINIMAX_BASE_URL or https://api.minimaxi.com/v1>/text/chatcompletion_v2`, `Authorization: Bearer $MINIMAX_API_KEY`. Sends vision via base64 `image_url` content parts. **Use a vision model (`MiniMax-M3`)** — `MiniMax-M2.7` (the anthropic-endpoint runner's default) is text-only. M3 is a reasoning model: its answer text lives in `message.content`, separate from `reasoning_content`.
- **`max_tokens` policy (do not cap): never set a `max_tokens` ceiling for any model — for predictions, extraction, or judging — unless explicitly required.** A cap starves reasoning models (M3 spends the budget on hidden `reasoning_content` and returns empty `content`), which surfaces as bogus "empty reply" / "unparsed" judge failures. `extraction_max_tokens(model, default)` in `scripts/eval/providers.py` therefore **always returns `None`** (the `default` arg is ignored, kept only to document intent); `--max-tokens` defaults to `None` for predictions. The **one** exception is `deepseek-v3.2`, pinned to `max_tokens: 32768` via `_MODEL_PARAMS` — a hard gateway requirement (omitting it makes the gateway inject an illegal 65536 and 400 every request), not a starvation cap. To reinstate any other cap, do it explicitly at the call site.
- **`--no-images` (text-degraded variant, opt-in only).** Withholds every image so a text-only model can be probed on a multimodal benchmark (glm-5.2 `400 InvalidParameter: Model only support text input` on all 4,055 OlympiadBench `OE_MM_*` items, 2026-07-21). Implemented as `strip_image_parts()` in `scripts/eval/runner.py`, applied **after** `build_messages` — a flag inside `BenchmarkAdapter` would silently miss the eight adapters that override it (k12vista and mmtutorbench among them). **The score is a degraded proxy, not a capability measure**: items whose image carries essential information become unanswerable, so it is never comparable with a standard run nor with a vision model — see memory `gateway-model-vision-capability` on never scoring a text model 0 on a multimodal set. Three constraints enforce that: output is auto-isolated to `reports/eval/<benchmark>/_noimage/<model-slug>/`; an explicit `--out-dir` inside `reports/eval/` without a `_noimage` segment is refused; and `summary.json` records `input_variant: no_images` + `input_variant_note`, with a mixing guard (mirroring the judge-model one) that refuses to reuse a predictions cache made under the other variant. `report.html` renders a warning banner. Variant naming follows the `PROMPT_VARIANT` / `ASAP_PROMPT_VARIANT` precedent.
- Add a benchmark by writing `scripts/eval/benchmarks/<name>.py` (a `BenchmarkAdapter` subclass: `load_items` / `build_messages` / `extract_answer` / `score` / `buckets`) and registering it in `scripts/eval/benchmarks/__init__.py`. The MathVista adapter ports the official `evaluation/` extraction (few-shot `ext_ans.demo_prompt`) and scoring (`normalize_extracted_answer` + nearest-choice edit distance), reimplemented in `scripts/eval/scoring.py` with no extra deps. - Registered **ASAP 2.0 adapter** (essay scoring, model-as-rater): **asap_2** scores the **official test split (7,421 essays, 5 prompts)** from the authors' repo `github.com/scrosseye/ASAP_2.0` — use that repo, **not** the Kaggle mirror `lburleigh/asap-2-0`, which is the same corpus already merged with no split column and no rubric. Headline is **QWK against human holistic scores**, a population statistic: `score()` leaves `correct` unset so the framework reports `accuracy: null` by design, and `extra_summary` computes QWK overall / per prompt / per source-condition plus exact and adjacent agreement and mean bias. QWK lives in `scripts/eval/scoring.py` as `quadratic_weighted_kappa` (shared with sas_bench, validated against sklearn). **Prompt provenance:** ASAP 2.0 is a corpus with **no official LLM protocol**, so there is no official prompt to port and `ASAP_PROMPT_VARIANT` picks one. That reproduction is verified: rescoring the imported `predictions.jsonl` for both MiniMax-M3 and glm-5.1 returns their published QWK to float epsilon, overall and per prompt. **Those observed ranges span train+test, not the evaluated split** — "The Face on Mars" tops out at 5 in test but 6 in train and the runner announced 1-6; scoping to test alone silently rejects a model's legitimate 6 as out-of-range (this cost a 3e-3 QWK drift until fixed). Never present this QWK as an official leaderboard number under either variant.
- **Bad-format retry is benchmark-local, by design.** Both adapters re-ask the *model under test* (via `adapter.model_under_test` + `build_client`, the `p07_selfcheck` pattern) when a reply does not parse, reproducing the external runner's `--bad-format-retries`; default 2, tunable via `ASAP_BAD_FORMAT_RETRIES` / `PEDAGOGY_BAD_FORMAT_RETRIES`, and skipped entirely when `model_under_test` is unset so `--score-only` never issues calls. It is deliberately **not** a harness feature: the shared runner retries transport errors, not unparseable content. Note this path was near-inert in the imported runs — 4 genuine bad-format attempts across 14,842 rows; their 1,372 retried glm-5.1 rows were `Connection refused`/timeouts, **not** `max_tokens` truncation (completion tokens p99 was 3,024 against their 4,096 cap), so running uncapped per repo policy does not compromise comparability.
- **Hazard: the imported result dirs are clobberable.** `reports/eval/{asap_2,pedagogy_benchmark}/<model>/` hold colleague runs imported by `scripts/import_external_pedagogy_asap_results.py`. Running the harness with a `--model` matching one of them **reuses its `predictions.jsonl` as cache and overwrites `scored.jsonl`/`summary.json`/`report.html`** with a partial run. `run_eval.sh` has no output-dir knob (`OUT_DIR` is ignored); use `scripts/eval_benchmark.py --out-dir <scratch>` when reproducing an existing model. The imported files are committed, so `git checkout --` restores them.

## Benchmark baselines (floors and ceilings)

Raw eval scores have no anchor on their own, so `data/benchmark_baselines_v1.json` records a floor for every benchmark in three layers — **L1 uniform random** (uniform over the item's own answer space), **L2 trivial strategy** (the best answer-independent constant: guess-from-prior / majority class / never-change / always-abstain), and **L3 degenerate reply** (junk generation scored by the real judge, for judge-scored tasks where uniform random is undefined). **L1 is not the binding floor for about half the set** — read L2 and the `note` field. Baselines are computed by driving the *real* `adapter.score()` / `extra_summary()` with synthetic answers, so RFS partial credit, macro-F1 and QWK all come out of the production code path; closed forms are cross-checks only (validated: the MathVista simulation reproduces the paper's published 17.9% chance level).

- `scripts/build_benchmark_baselines.py` (L1+L2, no API; `--validate-only` runs 10 regression assertions; `--merge` exists because olympiadbench must run in the antlr4==4.11 uv env)
- `scripts/build_human_baselines.py` → `data/benchmark_human_baselines_v1.json` (`version: v2`, 2026-08-15). Human numbers carry a comparability grade **A/B/C/D**; D never becomes a `human_score`, only a `context_anchor`. 6 of 21 literature entries have a usable human value — the rest are `null` with an `evidence` note recording which paper was checked, so nobody re-does the search. MRBench and BEA 2025 ship an `Expert`/`Novice` human tutor reply per dialogue, which the script scores on our own headline metric. **v2 added three things.** (1) `per_task_human` — AGIEval publishes per-task human average *and* top-1% (real exam score distributions, not a study), MathVista publishes per-task and per-skill human accuracy; the report re-weights them by *our* item counts, which is the only comparable form (AGIEval's blanket 0.67 is not — our run includes 1,000 MATH items the paper has no human number for). (2) `usability_thresholds` — a **separate table from the human anchors, never merged into one column**: the line a system must clear to be deployable, regardless of where humans land. Kinds are `field_standard` (AES QWK ≥ 0.70 from Williamson, Xi & Breyer 2012, which also asks for ≤ 0.10 degradation vs human-human — uncheckable for asap_2/sas_bench since neither publishes rater agreement), `inter_annotator` (kappa ≥ 0.61 Landis & Koch, with the dataset's own annotator agreement as the true ceiling: MRBench Cohen 0.71, BEA 2025 Fleiss 0.65), `construct` (mathtutorbench win_rate 0.5 = tied with the expert teacher), `institutional` (exam pass marks), `none` (no accepted threshold exists — say so rather than invent one). (3) A `reading_blocked` field on entries whose model-vs-human comparison is known-invalid (mrbench_tutor/bea2025_tutor prompt leak, mmtutorbench cross-judge, agieval task-mix, p08_abstention protocol asymmetry); the report prints the block text *in place of* the one-line verdict so a retracted conclusion cannot leak back in.
- **New human anchors found 2026-08-15 that were previously blank**: `p08_abstention`'s source dataset UMWP reports a **human F1 of 93.16%** (5 volunteers, 200 stratified items) on exactly the metric we already compute as `extra_metrics.abstention_f1` — the repo's own `score_10` composite has no human meaning (any content-independent strategy scores 5.0), but this one does, and no model reaches it. `edubench` has no human score but its paper's human study (198 samples, **1 annotator**, Kendall's W 0.63) states the LLM judge scores about **1 point higher than the human**, so our 7.26–8.72 reads as roughly 6.3–7.7 in human terms. `tutorbench`'s per-sample expert "golden tutoring response" is described in the paper but **not in the public JSONL** (rubrics only), so the same-pipeline human route is closed there. `mathtutorbench`'s `pref_test.jsonl` does carry `teacher_response_negative` (novice teacher), giving a runnable *lower* human anchor for the win-rate tasks — not yet run.
- `scripts/run_reference_baseline.py` (L3, **costs API quota**) → `reports/eval/_baseline/<benchmark>/<variant>/`. Variants `refusal`/`echo`/`generic` for the floor, `expert`/`novice` to re-score the dataset's human replies through *our* judge. There is deliberately no `empty` variant: `run_scoring` classifies a blank response as `no_prediction` and drops it from the denominator. **Pin the judge to match the run being anchored** — mrbench/bea2025 defaults are now `glm-5.2` but the historical runs used `MiniMax-M3`, and edubench's real 12-model set lives under `_judge-deepseek-v3.2/` while the top-level dir holds only a 5-item smoke run.
- `scripts/build_baseline_report.py` → `doc/benchmark_baselines_2026-08-04.md` (joins all three layers with the observed model range; filters smoke/truncated runs at 90% of the largest run's item count).
- `scripts/build_human_baseline_report.py` → `doc/benchmark_human_baselines_2026-08-15.md` (no API). The **ceiling-side sister report**, deliberately a separate document from the floor one: table A 人类参照锚, table B 可用门槛, then the per-task re-weighting, the same-pipeline expert re-scores, and an explicit "查过但确实没有" section so nobody repeats the literature search. It imports `observed_range` / `_headline_of` / `COVERAGE_FLOOR` from `build_baseline_report` rather than reimplementing them, so the two reports can never disagree about which runs count.
- `scripts/build_l1_floor_profile.py` → `reports/atomic_ability_l1_floor/` (no API). Pushes L1 through the *same* aggregation as the panel, so the floor lands per P01–P20, per benchmark and per cell in the published 0-10 units. **`build_site_payload.py` imports this module** to fill the website's `floor` block, and `validate_site_payload.py` cross-checks that block against these jsonl artifacts — so after a baseline change, rerun this script or the website sync fails validation.

Load-bearing findings: `p07_selfcheck` / `p08_calibration` / `p08_abstention` all floor at **5.0/10**, not 0 — and every p07 model scores 5.019–5.572, i.e. barely above "never change your answer". `mrbench_judge`/`bea2025_judge` majority-class gets 0.63–0.72 *accuracy* but only 0.26–0.28 macro-F1 (which is why headline is macro-F1; never compare their accuracy). `longtutor_teaching`'s accuracy is a parse-success rate (0.999–1.000), not a capability. This work deliberately **does not** change `normalize_score()` in the aggregation pipeline: chance-correcting P01–P20 would break comparability with R25 and is a separate decision.

## The atomic-ability mapping & rebenchmark pipeline

The per-benchmark eval results are aggregated into a 20-ability profile (**P01–P20**). Numbering has migrated twice: doc-scheme since R20 (2026-07-18), then **R24 (2026-07-19) re-sequenced it** when P04 多模态生成 was reworked and moved into the foundation group next to P03 — P01–P03 and P17–P20 kept their numbers, old P04–P15 each shifted up one, old P16 became P04. **Two translation tables are needed to read old notes**: pre-R20 (P01–P23 with tombstones, still the scheme used inside every `rationale` free-text field and in `scripts/build_rebenchmark_conclusion_plan.py`) → R20 → R24; both tables live in `doc/atomic_ability_mapping_final_2026-07-15.md` under the R20 and R24 records, and the R24 one is mirrored in the JSON's `schema_notes.numbering_R24`. Rationale text was deliberately never rewritten — P codes there are mixed into prose and a regex pass would corrupt them. Current-state reference: `doc/atomic_ability_mapping_v6_2026-07-19.md` (clean snapshot; its weight tables are script-regenerated from the JSON, and the R2x prose under each table keeps the numbers as they stood at that revision — read current values off the tables, not the prose). Adjudication history (R1–R25) lives in `doc/atomic_ability_mapping_final_2026-07-15.md`. **Single source of truth is `data/mapping_measurement_model_v6.json`** (`version: v6-R25`, 2026-07-19; v1–v5 are kept as pre-adjudication snapshots — never edit or delete them). R20 also **removed the four-level evidence-tier system**: effective weight = relevance × confidence only, no foundation-gate ×0.45, single `score_10` (no raw/tier_adjusted split), P artifacts renamed `09_atomic_p_scores.jsonl`/`10_group_scores.jsonl`; **R23 (2026-07-19) reversed the blanket judge-task exclusion**: `EXCLUDED_SCORING_BENCHMARKS` is now empty and exclusion is carried by per-cell `excluded` markers, because P11 主观题评价能力 measures judging ability itself — `bea2025_judge` (`extra_metrics.recommended_judge_score`) and `mrbench_judge` (`macro_over_dimensions.f1_macro`) score there (confidence 0.75 at R23, 1.0 since R25), and their construct-mismatched mounts on P10/P17 were deleted. Their macro-F1 scale (3.7–5.6) is harsher than the QWK/CCS cells (7.3–8.7) sharing that facet, so P11 dropped ~0.7–1.0 across the board at R23 — a metric-scale change, not a regression, and not comparable across R23. P01 is ifeval-only (single-source direct measurement).

**R25 (2026-07-19) made both weights rule-derived — do not hand-tune either.** *Relevance* (cell `weight` in the JSON) uses five tiers: 1.0 exact construct match, 0.8 strong, 0.5 moderate, 0.2 weak (you must be able to state in one sentence what the facet's signal in that metric is), 0 = not mounted at all (an exclusion, not a weight). *Confidence* (`default_benchmark_weight` in the aggregation script) starts at 1.0 and two factors deduct 0.15 each: **scoring method** — objective rule scoring deducts nothing, LLM-as-judge deducts, classified by the *actual* scoring path rather than the benchmark's nominal description (an LLM that merely extracts an answer which a rule then compares to gold stays objective — mmlu_pro's regex fallback, eduguard_sata's verbose replies, mathvista's official protocol; longtutor_evidence emits CORRECT/INCORRECT itself and is therefore a judge); and **quality** — externally vetted data and gold (official release, peer review, human annotation) deducts nothing, self-built and self-judged deducts. That yields exactly 1.0 / 0.85 / 0.7 plus one documented exception (`edubench · error_identification_correction_accuracy` = 0.3, R23). Contamination risk, protocol fidelity, and measured judge noise (judge-swap ρ, kappa, BLEU validity) are deliberately **excluded from the weights** and live in rationale notes only. To change a confidence value, change the benchmark's scoring-method or quality classification and say why — never edit the number alone. Scores are **not comparable across R25**; the pre-R25 snapshot is `reports/atomic_ability_rebenchmark_2026-07-08_v6r24_snapshot_20260719`. Facet-level rules (R19): a facet split must be *boundary-decidable* (every task has exactly one home; open-ended scenario axes don't qualify) and *non-duplicative* (two facets must not be the same construct twice); borderline proxy cells are left out rather than mounted.

**R26 (2026-08-04) replaced the missing-cell rule: no more borrowed scores.** R22 used to fill a panel model's missing cell with the lowest score any tested model got there (`IMPUTE_MIN_FACES`, `source_type: imputed_min`) — that value was neither the model's result nor an honest blank, and it handed MiniMax-M2.7 / GLM-5.2 / DeepSeek-V4-Pro a 5.08 on P03 多模态理解 when none of the three can even accept an image. A missing cell is now classified by **the benchmark, not the P**: `capability_gap` (the model lacks a capability *every* item in that cell needs — vision only so far) **scores 0 and counts**, propagating through the ordinary relevance × confidence weights to **every** P the cell is mounted on, with no construct-scope exemption (so mathvista/k12vista zeros also land on P05/P06/P14/P16 — P06 drops ~1.5 for the three blind models, by design); everything else is `untested` — **no score, no denominator, never substituted and never zeroed**, listed per cell in `09_atomic_p_untested_cells.jsonl`. A P whose cells are all untested emits a row with `score_10: null` and `coverage_status: untested` so reports print 未测过 rather than dropping the model. Cells where only *some* items need the capability (tutorbench, olympiadbench overall) stay `untested` — a text model earns a genuine non-zero score there, so 0 would be a measurement artifact. Capability tables are `MODEL_CAPABILITIES` (probe results, `True/False/None`; only `False` ever zeroes) and `CELL_CAPABILITY_REQUIREMENTS` (`REQUIRE_ALL` vs `REQUIRE_PARTIAL`, keyed by `benchmark_id` or the more specific `(benchmark_id, subdimension)`). **Classify by what the generation pipeline actually sends the model under test, not by what the task is called** — eduillustrate emits Manim *code* and reads like a text task, but all 230 problems carry a base64 diagram that `explanation_planner.py` and `code_generator.py` both attach, and the text carries only `question` (`img_caption` never reaches the prompt), so it is `REQUIRE_ALL` and the three blind models score 0 on P04 (and on its P16 artifact-generation side-mount). New p_row fields: `capability_zero_count` / `capability_zero_weight_share` / `untested_cell_count` / `untested_cells` / `coverage_status` (the old `imputed_*` fields are gone). Two related fixes shipped with it: `--no-images` text-degraded runs (`summary.input_variant == "no_images"`) are now excluded from multimodal cells alongside `BLIND_VISION_MODELS` (glm-5.2's 6.35 was leaking into P03), and `full_panel` in the explorer now means "member of `PANEL_MODEL_KEYS`" rather than "has a score on every P" — those coincided only because imputation filled every gap. Scores are **not comparable across R26**; the pre-R26 snapshot is `reports/atomic_ability_rebenchmark_2026-07-08_v6r25_snapshot_20260804`.

Before rerunning after a mapping revision, snapshot `reports/atomic_ability_rebenchmark_2026-07-08/` to `*_vN_snapshot_YYYYMMDD/`. ## Conventions specific to this repo

- **Standard-library-first Python 3**, four-space indent. JSONL for row-oriented benchmark data; Markdown+HTML pairs for reports.
- **Dated snapshot names are intentional** (`benchmark_v1_2026-05-18`, `*_2026_05_18.py`). Don't rename or "clean up" the dates — they version the artifacts.
- Small model/prompt experiments go under `reports/re_benchmark_v1/experiments/<name>/`, preserving raw `predictions.jsonl`, `run_summary.json`, `scored_items.jsonl`.
- `sources/datasets/` holds downloaded dataset copies; it is gitignored and not committed.
- Credentials (e.g. `MINIMAX_API_KEY`) come from env vars only.

## Interpretation guardrails (from README)

- Never average raw scores across different benchmarks — map to D01–D24 capabilities first, then form a capability profile.
- General-knowledge benchmarks are gate items only; they do not prove teaching ability. Core teaching capability lives in error diagnosis, scaffolding, feedback quality, personalization, multimodal grounding, safety boundaries, and real learning outcomes.

## The edubenchassistant skill

`skills/edubenchassistant/SKILL.md` is an Agent skill: given an AI-education app/product/scenario, it uses this repo's evidence base to recommend which D01–D24 capabilities and S1–S8 scales matter, what prior benchmarks exist, native metrics/public results/data availability, and safety/contamination/rubric concerns — emitting an HTML report into `reports/edubenchassistant/`. Newly discovered evaluation gaps are logged to `benchmark-todo.md`.
